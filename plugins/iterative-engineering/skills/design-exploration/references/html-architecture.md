# HTML Architecture Reference

The design exploration gallery is built from a **fixed shell template** (`references/shell-template.html`) with variation content rendered in iframes. Each variation is a complete HTML page stored in a `<template>` element and loaded into an `<iframe srcdoc>`. This document covers the generation architecture, template placeholders, and variation content guidelines.

> **CONSISTENCY RULE:** The gallery shell — sidebar, top bar, rating bar, control panel, export modal, shortcuts overlay — is defined by the template and must be **identical across every file**. Only the variation content inside the iframe changes. The template IS the spec.

## Tech Stack

| Layer | Choice |
|-------|--------|
| Structure | Single HTML file, ~3000-5000 lines |
| Styling | Tailwind CSS Play CDN (shell) + per-variation Tailwind CDN (in iframes) |
| Reactivity | Alpine.js CDN (shell only) |
| Shell Fonts | DM Sans + JetBrains Mono (Google Fonts, fixed) |
| Variation Fonts | Per-variation Google Fonts (each iframe loads its own) |
| Variation Rendering | `<template>` elements + `<iframe srcdoc>` |
| Icons | Inline SVG or Unicode |
| Storage | localStorage for ratings, notes, control states, panel position |

## Generation Architecture

The HTML file is generated by an **orchestrator + parallel subagents** pattern.

### Orchestrator Responsibilities (Opus)

The orchestrator writes and owns the file. It:
1. Copies `references/shell-template.html`
2. Fills in the three template placeholders (see below)
3. Writes the completed file to disk

The orchestrator does NOT generate shell HTML — that's in the template. It does NOT generate variation content — that's delegated to subagents.

### Subagent Responsibilities (Sonnet, one per variation)

Each subagent generates content for exactly one variation and **writes 2 files** in the exploration directory. The subagent has no knowledge of the shell, Alpine.js, or other variations.

### Subagent Output Contract

Each subagent writes two files. The orchestrator never reads these into its own context — assembly happens via bash/python file operations.

**1. `_var-{ID}.html`** — a complete HTML page (rendered inside an iframe):

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <script src="https://cdn.tailwindcss.com"></script>
  <link rel="preconnect" href="https://fonts.googleapis.com">
  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
  <link href="https://fonts.googleapis.com/css2?family=Playfair+Display:wght@400;700&family=DM+Sans:wght@400;500&display=swap" rel="stylesheet">
  <style>
    :root {
      --bg: #faf9f7;
      --text: #2d2a26;
      --accent: #62929e;
      --font-heading: 'Playfair Display', serif;
      --font-body: 'DM Sans', sans-serif;
      /* ... all custom properties ... */
    }
    :root * {
      transition: color 0.3s ease, background-color 0.3s ease,
                  border-color 0.3s ease, padding 0.3s ease,
                  gap 0.3s ease, font-size 0.3s ease,
                  border-radius 0.3s ease, box-shadow 0.3s ease,
                  max-width 0.3s ease, width 0.3s ease;
    }
    /* scrollbar styling, keyframes, etc. */
  </style>
</head>
<body class="min-h-screen bg-[var(--bg)] text-[var(--text)] font-[var(--font-body)]">
  <!-- Variation content -->
  ...
  <script>
    // Optional: JavaScript for interactive demonstrations
  </script>
</body>
</html>
```

**2. `_var-{ID}.js`** — a JavaScript object literal (no assignment, no semicolon, NO `html` field):

```javascript
{
  id: 'A1',
  family: 'A',
  familyName: 'Sidebar Classic',
  name: 'Shopify Morning',
  layoutType: 'Sidebar + Cards',
  aesthetic: 'Clean Light',
  description: 'Classic sidebar navigation with warm editorial card grid.',
  controls: [
    // 4-6 controls (see control schema in SKILL.md)
  ]
}
```

Temp files are cleaned up after assembly: `rm _var-*.js _var-*.html _metadata.json`

## Template Placeholders

The shell template contains three placeholders the orchestrator fills in:

| Placeholder | Location | What goes there |
|---|---|---|
| `__METADATA_JSON__` | `<script id="exploration-metadata">` | The exploration metadata JSON object (project, topic, round, date, variations array) |
| `__VARIATIONS_ARRAY__` | `variations: [...]` in the Alpine.js data model | All variation JS objects, comma-separated |
| `__VARIATION_TEMPLATES__` | After modals, before `<script>` | `<template id="tpl-{id}">` elements wrapping each variation's HTML page |

### Assembly (file-based — no reading variation content into orchestrator context)

Assembly uses the standalone `references/assemble.py` script. The orchestrator runs one command:

```bash
python3 {skill_root}/references/assemble.py "{dir}" {round} "{skill_root}/references/shell-template.html" && open "{dir}/v{round}.html"
```

The script handles everything in one call:
1. Copies the shell template to `v{round}.html`
2. Validates all subagent output: checks file existence (JS + HTML required per variation), checks HTML files for `</template>` (the only forbidden tag)
3. Wraps each HTML file in a `<template id="tpl-{id}">` element, extracting `<body class="...">` into a `data-body-class` attribute (the HTML parser strips `<body>` attributes inside `<template>` elements)
4. Replaces all three template placeholders with subagent file contents
5. Cleans up all temp files (`_var-*.js`, `_var-*.html`, `_metadata.json`)

Exit codes: 0 = success, 1 = missing files, 2 = validation failure, 3 = usage error.

The orchestrator never reads variation file contents into its own context. The script does all file I/O at the OS level.

## CSS Architecture

### Shell Styles (FIXED — in template)

All shell chrome uses `--shell-*` prefixed design tokens defined in `:root`. These are baked into the template and never modified.

### Variation Styles (CREATIVE — from subagents)

Each variation is a complete HTML page rendered inside an iframe. CSS custom properties are defined on `:root` within the variation's own page — **not scoped by class** (the iframe provides full CSS isolation). Variation properties use unprefixed names (`--bg`, `--text`, `--accent`) — never `--shell-*`.

```css
:root {
  --bg: #faf9f7;
  --bg-alt: #f0ece4;
  --text: #2d2a26;
  --text-dim: #8a8580;
  --accent: #62929e;
  --font-heading: 'Playfair Display', serif;
  --font-body: 'DM Sans', sans-serif;
  --sidebar-width: 240px;
  /* ... properties matching this variation's controls */
}
```

### How Controls Apply

The shell applies control values by calling `iframe.contentDocument.documentElement.style.setProperty()` for each control. The `applyControlsToIframe()` method runs on iframe load and on every control change. This means:

- Controls set CSS vars directly on the iframe's `<html>` element via `setProperty()`
- The inline style on `documentElement` has higher specificity than `:root` rules
- Child elements inherit the overridden values through normal CSS cascade

Examples:
- Range `{ value: 24, unit: 'px', cssVar: '--gap' }` → `setProperty('--gap', '24px')`
- Select (single) `{ value: 'teal', cssValues: { teal: '#4a9e8f' }, cssVar: '--accent' }` → `setProperty('--accent', '#4a9e8f')`
- Select (multi-var) `{ value: 'dark', cssValues: { dark: { '--bg': '#1e1e2a', '--text': '#e0ddd8' } }, cssVar: null }` → `setProperty('--bg', ...)` + `setProperty('--text', ...)`
- Toggle `{ value: true, cssVar: '--show-dividers' }` → `setProperty('--show-dividers', '1')`

**Select controls MUST include `cssValues`** mapping each option label to a CSS value (string) or multiple CSS values (object). Without it, the CSS var receives a label string (e.g. `--bg: warm`) which is meaningless to CSS. Use the multi-var object format when one control needs to change several properties together (e.g. mood/mode changing background + text + borders).

### Control Gotchas (for subagents)

1. **`id` is required.** Without it, `updateControl()` can't find the control. The template auto-generates from `label` as a safety net, but always provide `id`.
2. **Never use `unit: '%'` on range controls.** The `%` gets appended to the CSS var value, breaking `calc()` expressions. Use unitless values — the CSS can multiply by `1%` if needed.
3. **All visual states must use `var()`.** If `--accent` drives a button color, hover/active states must also use `var(--accent)` or `color-mix(in srgb, var(--accent) ...)`. Hardcoded colors in hover states don't update when the control changes.
4. **Every `cssVar` must be consumed.** If a control sets `--card-radius` but the HTML uses Tailwind `rounded-xl`, the control is dead. Use `rounded-[var(--card-radius)]` instead.
5. **Define properties on `:root`, not on a class.** The iframe provides isolation. Controls apply via `documentElement.style.setProperty()`, which sets inline styles on `<html>`. Class-scoped properties won't be reached.

### Smooth Transitions

Each variation's HTML must include transition CSS for smooth control changes:

```css
:root * {
  transition: color 0.3s ease, background-color 0.3s ease,
              border-color 0.3s ease, padding 0.3s ease,
              gap 0.3s ease, font-size 0.3s ease,
              border-radius 0.3s ease, box-shadow 0.3s ease,
              max-width 0.3s ease, width 0.3s ease;
}
```

This is included in each variation's `<style>` block (not in the shell template, since variations are in iframes).

## Variation HTML Guidelines

Variations are the **creative surface** — this is where divergent design thinking happens. The shell is fixed; the content inside is not. Each variation's HTML file must:

1. **Complete HTML page** — each variation is a full page rendered inside an iframe. Include `<!DOCTYPE html>`, `<html>`, `<head>`, `<body>`. Include Tailwind CDN and Google Fonts `<link>` in `<head>`.
2. **Scripts allowed** — `<script>` and `<style>` tags are permitted. Use JavaScript for interactive demonstrations (toggles, wizards, live calculations, etc.).
3. **Only forbidden tag: `</template>`** — the assembly script wraps each HTML file in a `<template>` element. A literal `</template>` would close the wrapper prematurely. If needed inside a `<script>`, escape as `<\/template>`.
4. **Tailwind-first styling** — use Tailwind utility classes for layout, spacing, colors, typography, borders, shadows. Custom CSS in `<style>` is for: CSS custom property definitions on `:root`, keyframe animations, transitions, scrollbar styling, and things Tailwind genuinely can't express.
5. **CSS custom properties for all theme values** — `var(--bg)`, `var(--text)`, etc. via Tailwind arbitrary values (`bg-[var(--bg)]`, `text-[var(--text)]`, `font-[var(--font-body)]`). Define on `:root`.
6. **Unprefixed property names** — `--bg`, `--text`, `--accent` — never `--shell-*`
7. **Same realistic data** — identical content across all variations for fair comparison. No lorem ipsum.
8. **Self-contained** — no external images. Use CSS gradients, inline SVG, Unicode.
9. **Structurally distinct** — different DOM hierarchy, navigation pattern, content arrangement per family
10. **Motion via CSS + JS** — hover transitions on interactive elements, one entrance animation with staggered `animation-delay`. JavaScript is also allowed for interactive demonstrations.
11. **Atmosphere** — visual depth via CSS gradients, layered shadows, backdrop-filter. Scale to scope — don't overdo it.
12. **Transition CSS required** — include `:root * { transition: ... }` for smooth control changes.

### Size Constraints

Each variation is generated by a subagent with limited context. Keep output compact:

| Section | Target | Hard Limit |
|---------|--------|------------|
| HTML page (complete) | 250-450 lines | 500 lines |
| Controls array (in JS) | 4-6 controls | 8 controls |
| **Total per file set** | **~300-500 lines** | **550 lines** |

Scale to scope: a full page with sidebar, nav, multiple content sections, and icons needs ~350-500 lines. A single component needs ~200-300 lines.

**The mockup must look like a real product, not a wireframe.** Use realistic content, inline SVG icons, and multiple content sections. But stay efficient:
- Tailwind utility classes replace most custom CSS — `p-6 rounded-xl shadow-lg bg-[var(--bg)]` replaces 5 lines of CSS
- A card grid with 3-4 cards demonstrates a layout — don't repeat 12 cards
- Use Tailwind's spacing/sizing utilities instead of writing custom CSS for every margin and padding
- Use Unicode (→ ● ◆ ▲) for simple decorative elements; reserve inline SVG for nav icons and key UI elements
